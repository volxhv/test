# Практическая работа 3 — GitLab CI/CD через Ansible и Docker socket

Учебный пример: Go + Vite + PostgreSQL + nginx. ПЗ 2 не было приложено, поэтому это самостоятельное минимальное приложение, а не копия ПЗ 2.

## Что автоматизировано

Один Ansible playbook выполняет настройку от начала до конца:

1. Создаёт SSH-ключ и запускает контейнеры GitLab CE, GitLab Runner, SSH-сервера деплоя и gateway.
2. Ожидает запуска GitLab, создаёт административный API-токен локально внутри GitLab.
3. Через API создаёт группу `devops`, приватный проект `devops-stack`, защищает `main` и теги `v*`.
4. Создаёт пароль PostgreSQL, устанавливает защищённые переменные `DB_PASSWORD`, `SSH_PRIVATE_KEY` и `SSH_KNOWN_HOSTS`. SSH host key берётся прямо из контейнера деплоя, не из непроверенного сетевого ответа.
5. Через API создаёт project runner с тегом `socket`, регистрирует его с Docker executor и настраивает 4 параллельные job.
6. Копирует файлы проекта в отдельную временную Git-копию, коммитит изменения и отправляет их в GitLab. Push запускает pipeline. Локальный Git-репозиторий пользователя не меняется.

Определение pipeline находится в `.gitlab-ci.yml`; сам экземпляр pipeline создаёт GitLab при push. Деплой остаётся **ручной job**, как требуется в методичке. Если исходники не изменились, повторный запуск Ansible не создаёт новый коммит или pipeline.

## Требования и безопасность

Рассчитано на одну **Linux-машину**, установленный и запущенный Docker Engine с Compose plugin и GitLab CLI-образы из интернета. Рекомендуется 8 ГБ ОЗУ или больше и свободное дисковое место. Свободные порты: 8080, 5050, 2222, 2224, 8443, 8444, 9443, 9445. Каталог проекта должен иметь абсолютный путь без пробелов и быть доступным локальному Docker daemon. Windows/macOS Docker Desktop, удалённый демон и нестандартное расположение сокета специально не адаптированы.

Сокет `/var/run/docker.sock` даёт контейнерам и CI job практически полный контроль над хостом. Используйте только доверенную учебную машину и доверенный код в репозитории. GitLab и registry используют HTTP, TLS gateway самоподписанный, деплой использует root — это лабораторная конфигурация, не production. Пароли, API-токен и ключи хранятся в `secrets/`, он исключён из Git. Не публикуйте этот каталог и не передавайте его третьим лицам. API-токен действует 365 дней; его надо заменить до истечения.

## Запуск из PyCharm

Распакуйте архив, откройте папку проекта в PyCharm и выполните в его терминале:

```sh
export PROJECT_DIR="$(pwd -P)"
docker compose -f compose.control.yml run --rm --build ansible
```

При первом запуске скачиваются образы, а GitLab может стартовать несколько минут. Ansible ожидает страницу входа до 15 минут; если GitLab не успел загрузиться, запустите команду ещё раз.

После успешного выполнения откройте **http://localhost:8080/devops/devops-stack** и войдите как `root`. Первоначальный пароль:

```sh
docker compose -p practice3-infra -f infra/compose.yml exec gitlab cat /etc/gitlab/initial_root_password
```

Задайте новый пароль в GitLab сразу: файл первоначального пароля временный и может исчезнуть после перезапуска. Ansible не печатает и не меняет этот пароль.

В GitLab откройте Build → Pipelines: push от Ansible создаёт pipeline автоматически. В Build → Runners отображается project runner `practice3-socket-runner` с тегом `socket`. Убедитесь, что verify и build завершились успешно, затем вручную запустите `deploy`. Приложение: **https://localhost:8443/** (для учебного сертификата нужно принять предупреждение браузера).

Повторное применение после изменений:

```sh
export PROJECT_DIR="$(pwd -P)"
docker compose -f compose.control.yml run --rm --build ansible
```

Ansible загрузит изменённые файлы и запустит новый pipeline. При копировании существующие файлы перезаписываются файлами из проекта; удаление файлов локально не удаляет их из GitLab. Не используйте автоматическую публикацию поверх чужого проекта с тем же именем без понимания последствий.

## Pipeline и сценарии

* `lint:go`, `lint:frontend`, `test:unit` и сбор списков зависимостей идут независимо; файлы `go.mod.all` и `npm.ls` сохраняются как артефакты на 7 дней. Блокировка frontend-зависимостей — `package-lock.json`.
* Сборки backend, frontend и nginx отправляют образы в registry с тегом короткого SHA коммита или git-тегом. Все сборки зависят от lint и unit-тестов. Backend и frontend собираются multi-stage; nginx — отдельный простой образ конфигурации.
* `deploy` запускается вручную из основной ветки или из тега вида `v1.2.3`, поднимает выбранный цвет, проверяет его и переключает gateway. `smoke` проверяет HTTPS после deploy. Доступ к портам цветов напрямую — HTTP: blue `localhost:9443`, green `localhost:9445`.
* **Релиз:** после создания тега `v1.2.3` и push в GitLab запустите ручной deploy из pipeline тега. Для последующих обычных коммитов можно менять файлы локально и повторять запуск Ansible.
* **Откат по тегу образа:** при запуске ручной job `deploy` укажите `ROLLBACK_TAG` = предыдущий короткий SHA или релизный тег; при необходимости `DEPLOY_COLOR` = `blue` либо `green`. Три старых образа должны оставаться в registry. Для повторного запуска job с переменными используйте форму Retry с переменными, если она доступна; иначе запустите новый pipeline для того же коммита с переменными.
* **Canary:** после первого deploy выберите цвет работающего стека в `DEPLOY_COLOR` и запустите job `canary` из pipeline новой версии. Новый backend отдельно открывается по HTTP на 8444, выполняются 100 запросов к health API, успех — минимум 99. Gateway и пользовательский трафик не переключаются. После успешной проверки вручную запустите `deploy`, а затем `canary:stop`. Canary использует БД выбранного цвета и не делает миграций.
* **Blue/green:** если активен blue, запустите `deploy` с `DEPLOY_COLOR=green`. Новый стек поднимается на 9445, затем после проверки gateway переключается на green. Быстрый возврат к уже работающему blue:

```sh
docker compose -p practice3-infra -f infra/compose.yml exec deploy \
  sh /opt/devops-stack/remote.sh switch unused blue
```

  Базы blue и green изолированы отдельными томами и не синхронизируются. Переключение цвета не переносит данные; миграции и стратегия синхронизации в учебном примере не реализованы.
* **Fail fast:** внесите ошибку lint или unit-теста, повторно запустите Ansible; сборки не стартуют, пока не пройдут оба lint и unit-тест.

Health API проверяет доступность PostgreSQL через `pg_isready`; это не тест бизнес-логики или SQL-запросов приложения. Не считайте успешный smoke доказательством корректности данных.

## Особенности и диагностика

Ansible использует Docker daemon хоста через socket binding; Docker-in-Docker и `privileged` не используются. Docker должен быть установлен заранее: playbook не меняет apt-зеркала и не устанавливает daemon на хост, в отличие от варианта с виртуальной Ubuntu. Для работы registry на `localhost:5050` Docker хоста должен разрешать обращения к локальному HTTP registry; localhost обычно считается локальным insecure registry. Доступность registry зависит от конкретной конфигурации Docker.

```sh
export PROJECT_DIR="$(pwd -P)"
docker compose -p practice3-infra -f infra/compose.yml ps
docker compose -p practice3-infra -f infra/compose.yml logs --tail=100 gitlab
docker compose -p practice3-infra -f infra/compose.yml logs --tail=100 runner
docker network inspect practice3-net
```

Gateway возвращает 503 до первого деплоя и после его пересоздания; повторно выполните `switch` на запущенный цвет. Для остановки инфраструктуры без удаления данных: `docker compose -p practice3-infra -f infra/compose.yml down`. Не удаляйте `secrets/` или тома Docker отдельно от GitLab: в них токены и ключи, связанные с его настройками. Для полного сброса требуется осознанно удалить все данные GitLab, runner и секреты; это уничтожит проекты и историю.

SSH-ключ и токены создаются только в `secrets/`, CI-переменные передаются GitLab API и не выводятся в логи Ansible. `SSH_PRIVATE_KEY` — File + Protected, но многострочный ключ не маскируется GitLab; не выводите его в job. CI environment-файлы на узле деплоя имеют права 0600. Продление или замена административного токена автоматически не реализованы.
